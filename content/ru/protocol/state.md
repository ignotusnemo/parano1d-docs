# Переход состояния

Состояние консенсуса — разреженный Merkle-вектор записей UTXO. Его активный
домен содержит `2^log_slots` листьев, где `log_slots` изменяется от 24 до 32.
После каждого блока заголовок фиксирует корень, число живых записей и счётчик
аллокатора.

## Состояния листа

Лист либо канонически пуст, либо содержит:

```text
{amount: u64, creation_id: u64, owner: 32 bytes}
```

Commitment упаковывает сумму и идентификатор создания в один lane `GF(2^128)` и
хеширует его вместе с владельцем под доменом UTXO-листа.

## Порядок перехода

Консенсус выводит из блока один упорядоченный переход:

1. проверить и выделить основную награду;
2. при наступлении срока проверить и выделить development-выплату;
3. обработать пользовательские группы `PagedSpend` в порядке блока;
4. очистить каждый использованный вход;
5. назначить новые идентификаторы создания и установить выходы;
6. обновить корни сегментов, число живых записей и счётчик аллокатора;
7. восстановить глобальный корень состояния.

Атомарность логической транзакции сохраняется, хотя её физические страницы
являются последовательными записями блока.

## Правила входов

Каждый живой пользовательский вход обязан:

- находиться в домене родительского состояния;
- указывать на занятый в данный момент слот;
- совпадать по заявленной сумме и общему владельцу;
- совпадать с текущим `creation_id`;
- встречаться в блоке только один раз;
- быть авторизован доказательством кошелька своей группы.

Записи награды и development-выплаты не имеют входов и проверяются по
системному расписанию.

## Правила выходов

Каждый живой пользовательский выход обязан:

- находиться в домене дочернего состояния;
- указывать на слот, пустой с учётом более ранних действий блока;
- иметь ненулевое значение;
- встречаться в блоке только один раз.

Аллокатор выбирает новый монотонный `creation_id`. Подсказки выходных слотов
лишь помогают при построении; блок всё равно обязан доказать их пустоту
относительно точного родителя.

## Сохранение значений

Внутри каждой логической пользовательской группы:

```text
sum(inputs) = sum(outputs) + fee
```

Во всём блоке созданное значение ограничено субсидией протокола. Верхняя
граница основной награды включает долю майнера и доступные ему комиссии.
Сожжённая комиссия за рост состояния из этой границы исключается.

Все агрегированные денежные вычисления используют ширину, в которой сумма
валидных полей `u64` не может незаметно насытиться.

## Сегменты

Листья объединены в сегменты по `2^16` слотов. Один блок может затронуть не
более 256 разных сегментов. Это консенсусное ограничение доступности проверяется
до загрузки данных сегментов.

Пустые сегменты используют канонический корень пустого поддерева и не требуют
сырого столбца MDBX. Сегмент удаляется после расходования последнего живого
UTXO.

## Правило расширения

Для дочернего кандидата родителя высоты `H` используются 18 жёстко
финализированных заголовков, заканчивающихся на высоте `H - 18`. Первое полное
окно доступно при высоте родителя 35 и покрывает высоты 0–17.

Подсчитываются заголовки, удовлетворяющие:

```text
active_slot_count × 4 >= 2^log_slots × 3
```

Если условие выполняется как минимум для 10 из 18 заголовков и
`log_slots < 32`, дочерний блок обязан установить
`log_slots = parent.log_slots + 1`. Иначе он сохраняет значение родителя.

При расширении предыдущий корень становится левым потомком нового корня, а
каноническое пустое поддерево — правым. Существующие индексы слотов и записи не
перемещаются.

## Данные реорганизации

Недавние undo-записи сохраняют предыдущую форму каждого затронутого слота,
корня сегмента и счётчика. Они хранятся 36 блоков, тогда как консенсус допускает
откат не более 17 блоков.

Undo — локальные данные восстановления, а не альтернативный witness
консенсуса. Замещающей ветви всё равно нужны валидные заголовки, работа и
терминалы.
